# Проверка конфликтов и переименованных Live Photos

При объединении нескольких экспортов macOS может встретить одинаковые имена и переименовать только один компонент Live Photo.

Пример:

```text
IMG_8271.HEIC      — отдельная фотография
IMG_8271 2.HEIC    — фотография настоящей Live Photo
IMG_8271.MOV       — видео настоящей Live Photo
```

Одинаковое имя больше не считается главным доказательством пары. Импортёр сначала использует уникальный Apple `ContentIdentifier`, поэтому `IMG_8271 2.HEIC` и `IMG_8271.MOV` объединятся, когда их metadata подтверждает связь. Исходники при этом не переименовываются и не изменяются.

## Запустить отдельную проверку

Из корня проекта:

```bash
cd ~/Projects/memory-site
source .memory-venv/bin/activate
python tools/audit_live_photos.py "$HOME/Projects/memory-source" --open
```

Команда только читает metadata и создаёт локальные отчёты:

```text
.memory-audit/live-photo-audit.html
.memory-audit/live-photo-audit.json
.memory-audit/live-photo-audit.csv
```

Папка `.memory-audit` не попадает в Git и не нужна на production-флешке.

## Что показывает отчёт

### Переименованные точные пары

HEIC/JPG и MOV имеют один уникальный `ContentIdentifier`, но разные имена. Такие пары импортёр восстановит автоматически. Переименовывать их вручную не нужно.

### Конфликтные семейства имён

Рядом обнаружены варианты вроде:

```text
IMG_8271
IMG_8271 2
IMG_8271 (2)
IMG_8271_2
```

Если Apple ID точно определил пару, отчёт помечает семейство как уже восстановленное. Если ID отсутствует или неоднозначен, импортёр не угадывает и оставляет все файлы отдельными. Проверять вручную нужно только эти строки отчёта, а не весь архив.

### Вероятные одинокие Live MOV

Короткое видео до примерно 6,5 секунды осталось без надёжной фотографии-пары и при этом имеет Apple ID либо находится в конфликтном семействе. Это не стопроцентная ошибка, но хороший список для ручной проверки.

### Неоднозначный ContentIdentifier

Один Apple ID встречается у нескольких изображений или нескольких видео. Такие файлы не объединяются автоматически, чтобы ни один источник не исчез из книги.

## Правила безопасного импорта

1. Уникальная пара `одна картинка + одно видео` с одинаковым Apple ID объединяется независимо от имени.
2. Совпадение имени используется только при отсутствии ID, близком времени и отсутствии вариантов ` 2`, `(2)`, `_2` и подобных.
3. Любая неоднозначность означает: все файлы остаются отдельными.
4. Исходная папка никогда не изменяется.

## Аудит встроен в основной запуск

Команда:

```bash
python tools/import_with_locations.py dry-run "$HOME/Projects/memory-source"
```

сначала обновляет отчёт Live Photos, затем выполняет обычный dry run.

То же происходит перед тестовым и production-импортом:

```bash
python tools/import_with_locations.py test "$HOME/Projects/memory-source" --open
python tools/import_with_locations.py import "$HOME/Projects/memory-source"
```

Повторное чтение отчёта можно пропустить только осознанно:

```bash
python tools/import_with_locations.py test "$HOME/Projects/memory-source" --skip-live-audit
```

Для финального импорта пропускать аудит не рекомендуется.

## Уже переименованный вручную файл

Переименование вроде `IMG_8271 2.HEIC` → `IMG_9999.HEIC` обычно не удаляет внутренний `ContentIdentifier`. Если ID сохранился, скрипт всё равно найдёт соответствующий MOV и покажет пару в разделе с различающимися именами.

Не продолжай массово переименовывать остальные файлы: сначала запусти аудит и работай только с действительно неразрешёнными группами.
